### Environment caveat 1 — Docker registry unreachable

The Docker daemon **is** running, but image pulls fail because DNS resolution for the registry
is blocked:

```
Error response from daemon: failed to resolve reference "docker.io/library/mysql:9.5":
failed to do request: Head "https://registry-1.docker.io/v2/library/mysql/manifests/9.5":
dial tcp: lookup registry-1.docker.io on 10.69.0.2:53: read: connection refused
```

Per the report instructions, the Docker/Testcontainers-dependent tests were therefore excluded:

- `org.springframework.samples.petclinic.MySqlIntegrationTests` — uses `@Testcontainers` with
  `MySQLContainer`.
- `org.springframework.samples.petclinic.PostgresIntegrationTests` — uses Spring Boot Docker
  Compose (`spring.docker.compose.skip.in-tests=false`).

Worth noting: `PostgresIntegrationTests` guards itself with
`assumeTrue(DockerClientFactory.instance().isDockerAvailable())`. That guard is **not**
sufficient here — the daemon is available, so the assumption passes and the test then fails
on the image pull. This is a latent CI fragility rather than a product bug, but it means the
suite is not self-healing in registry-restricted environments.

**These two classes are unverified in this run.** Their status should be considered unknown,
not passing.

**1. Spring Boot 4.0.3 → 4.0.8.** The pin is current-major but five patch releases stale. This
version also sits on the boundary of two actuator authentication-bypass CVEs, and the advisory
sources genuinely disagree about which release contains the fix:

- **CVE-2026-22731** — Authentication Bypass under Actuator Health groups paths (HIGH, CVSS 8.2,
  CWE-288). Spring's own record and the GitHub/NVD advisories list the affected range as
  *"from 4.0 before 4.0.3"*, i.e. **4.0.3 is already patched**. Snyk and the GitLab advisory
  database instead recommend **4.0.4 or higher** as the safe 4.0.x target.
- **CVE-2026-22733** — a related but distinct bypass under Actuator CloudFoundry endpoints, with
  different preconditions and version ranges.

This project does have the actuator on the runtime classpath (`build.gradle:41`, `pom.xml:44`)
and exposes all endpoints via `management.endpoints.web.exposure.include=*`
(`src/main/resources/application.properties:19`). However, **the documented exploit preconditions
for CVE-2026-22731 are not met**: exploitation additionally requires a custom health group with a
`management.endpoint.health.group.<name>.additional-path` on the main server *plus* an
authenticated application endpoint mapped beneath that path. This project configures no health
groups and no additional paths, so it is not believed to be exposed. Upstream also notes the
required configuration pattern is uncommon in practice (EPSS 0.00334, not in CISA KEV).

*Recommendation:* schedule a routine bump to 4.0.8 — it resolves the version-boundary ambiguity
outright and picks up ~5 releases of fixes. Not urgent for this codebase's configuration.

**2. Bootstrap 5.3.8 — up to date.** 5.3.8 is the newest release on the 5.3 line and the current
stable Bootstrap overall. No 5.3.9 has shipped; upstream effort has moved to a 6.0.0-alpha branch
with no released npm artifact and no announced date. Bootstrap 6 will be a breaking change
(responsive infixes become Tailwind-style prefixes: `col-md-6` → `md:col-6`). **No action.**

**3. Font Awesome 4.7.0 — a nuance worth stating precisely.** This is *not* a simple stale pin.
The `org.webjars.npm:font-awesome` webjar wraps the npm package `font-awesome`, which was itself
last published at 4.7.0 roughly a decade ago and is a third-party (unofficial) package. **4.7.0
is the newest version of the artifact the build actually references** — a version bump alone is
impossible. Font Awesome v4 is end-of-life; the official package is
`@fortawesome/fontawesome-free` (now 7.3.1), and v6 is in LTS.

Moving forward would be a migration, not an upgrade: the group/artifact changes, icon class
prefixes changed at v5 (`fa` → `fas`/`far`/`fab`), many icon names were renamed, and asset paths
differ — meaning template changes across the Thymeleaf views. Reasonable to defer, but it should
be tracked as a deliberate, permanent choice to ship EOL icon assets rather than an oversight.
