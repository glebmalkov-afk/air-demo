### Docker/Testcontainers tests were skipped

The Docker daemon is running in this environment, but it cannot reach the registry:

```
Error response from daemon: failed to resolve reference "docker.io/library/mysql:9.4":
dial tcp: lookup registry-1.docker.io on 10.69.0.2:53: read: connection refused
```

No images are cached locally (`docker images` is empty), so Docker is effectively unavailable
for Testcontainers. A first, unfiltered `./gradlew test` run confirmed this: 58 tests
completed, 3 failed, and all three failures were infrastructure failures, not assertion
failures:

- `MySqlIntegrationTests > initializationError` —
  `org.testcontainers.containers.ContainerFetchException: Can't get Docker image:
  RemoteDockerImage(imageName=mysql:9.6, ...)`. Note that the class is annotated
  `@Testcontainers(disabledWithoutDocker = true)`, but that guard does not help here: the
  daemon *is* present, only the image pull fails.
- `PostgresIntegrationTests > findAll()` — `IllegalStateException: Failed to load
  ApplicationContext`, caused by `ProcessExitException` from `spring-docker-compose`
  starting the `postgres` service.
- `PostgresIntegrationTests > ownerDetails()` — same context failure
  (`ApplicationContext failure threshold (1) exceeded`).

The reported 55/55 figure comes from a clean re-run with those two classes excluded via a
throwaway Gradle init script (`--init-script`, outside the repository); no build file was
touched. **The MySQL and PostgreSQL integration paths are unverified as of this report.**

### Environment note: JDK 17 toolchain

The first invocation of `./gradlew test` failed during configuration, before any test ran:

```
Cannot find a Java installation on your machine (Linux 6.17.0-1017-aws amd64) matching:
{languageVersion=17, vendor=any vendor, ...}. Toolchain download repositories have not been configured.
```

Only JBR 25.0.2 was installed, `build.gradle` requires a Java 17 toolchain, and no toolchain
resolver (e.g. Foojay) is configured in `settings.gradle`. Temurin 17.0.20.1+1 was downloaded
into `~/.jdks/` so Gradle's auto-detection could pick it up; all figures above are from that
JDK. This is an environment gap, not a repository defect — but any CI image running this build
must ship a JDK 17, or the build fails at configuration time.
